⭐ 任务一 · 把 Key 藏好（安全规范）

① .env 是否在 .gitignore 中：✅ 是。git check-ignore backend/.env 返回 backend/.env，证明它已被忽略，永远不会进 Git。

② 前端代码里是否残留 Key：✅ 无。对全项目执行 grep -rn "sk-vffy" --exclude-dir=node_modules，除 backend/.env 外 0 命中；对 Git 追踪的全部文件再搜一遍也是 0 命中。

③ Key 截图打码：本作业中 Key 一律显示为脱敏形式：sk-vffy**************cjxj（真实 Key 只存在于 backend/.env 一个地方）。

④ 我找到的 3 处"可能泄露 Key 的地方"：

  • 写进前端 JS/HTML：网页源码是公开的，按 F12 打开 Sources 一眼就能看到，等于把钥匙贴在门上；正确做法是 Key 只放 backend/.env，前端只请求自己的后端接口。
  • .env 忘记加 .gitignore 就 git commit：一旦提交，即使后续删除，Key 也永久留在 Git 历史记录里，推到 GitHub/Gitee 后任何人翻历史都能翻到；正确做法是建项目第一天就写好 .gitignore。
  • 截图 / 聊天群 / 文档里贴 Key 原文：终端 curl 命令里带着 Authorization 头直接截图、把 Key 原文发班级群或写进 README/AGENTS.md，都会让 Key 永久扩散；正确做法是一律打码成 sk-****。

⭐⭐ 任务二 · 客服人设改造（提示词工程）

① system 提示词全文（存放在 backend/app.js 的 XZR_PERSONAS.foodstreet，页面 customer-service.html）：

你是"中华美食街"在线客服。你只回答三类问题： ①营业时间（每天 10:00-22:00，节假日不休）； ②招牌菜（北京烤鸭 88 元、四川火锅人均 90 元、广东早茶人均 45 元、兰州拉面 18 元）； ③配送范围（门店 5 公里内免费配送，超出收 5 元配送费）。 遇到这三类以外的问题（闲聊、写作业、问路、其他店铺等）， 要礼貌说明"抱歉，我是美食街客服，只能回答营业时间、招牌菜、 配送范围三类问题，其他需求请在留言板留言"，并引导用户留言。

② 5 个问题实测结果（3 个该答、2 个该拒，全部真实接口返回）：

问题预期模型实际回答（摘录）判定
你们几点营业？该答"每天的营业时间是 10:00-22:00，节假日不休"✅ 答对

③ 为什么这样写能"管住"模型？四个原因：

  • 先定身份：开头"你是中华美食街在线客服"给模型设了角色，角色比命令更持久——模型后续每句回答都会代入这个身份。
  • 白名单 + 给足事实：明确列出"只答三类"，并把每类的准确数据（时间、菜价、配送费）直接写在提示词里，模型照着念即可，不需要也不倾向于自由发挥编造。
  • 给现成的拒绝话术：范围外问题最怕模型"好心办坏事"（比如真给它写诗）。提示词里直接提供一句固定的拒答模板 + 引导留言的动作，模型遇到超纲问题就会套用这句台词，而不是即兴发挥。
  • 测试闭环：人设不是写完就信，必须用"3 该答 + 2 该拒"真实问题验证。实测 5/5 符合预期，说明这份提示词在 Qwen2.5-7B 上有效。

⭐⭐⭐ 任务三 · 多平台热切换 + 答辩三问（工程思维）

实现方式：后端 .env 里存两组配置（SILICONFLOW_* 和 QINIU_* 三件套），/api/chat 接口接收 provider 参数决定读哪一组；前端 ai-chat.html 只加了一个下拉框，切换时不改任何代码。

// backend/.env（两组配置并存） SILICONFLOW_BASE_URL=https://api.siliconflow.cn/v1 SILICONFLOW_MODEL=Qwen/Qwen2.5-7B-Instruct QINIU_CUSTOMER_SERVICE_BASE_URL=https://api.qnaigc.com/v1 QINIU_CUSTOMER_SERVICE_MODEL=qiniu/conatus-free // 前端切换（ai-chat.html） <select id="xzrProviderSelect"> <option value="siliconflow">硅基流动 · Qwen2.5-7B</option> <option value="qiniu">七牛 · conatus-free</option> </select> // 选中值作为 provider 字段发给后端即可

演示状态：硅基流动正常对话 ✅；七牛的配置三件套已写入 .env、切换链路已验证（切换后请求确实走了 QINIU 配置），等七牛 Key 申请下来填进 .env 重启即可照常对话（当前未配 Key 时会返回友好提示而不是白屏，这也是一种"能用"）。

答辩三问：

  • ① 为什么 Key 不能放前端？网页代码是公开的，按 F12 就能看到全部源码和网络请求。Key 写在前端等于把家门钥匙贴在门上，任何人都能复制去刷你的免费额度，甚至产生欠费。正确做法是 Key 只放后端 .env（.gitignore 排除），前端把问题发给自己的后端，由后端带 Key 转发——和数据库密码不进前端是同一个思路。
  • ② 多轮对话为什么要把历史消息一起发？因为大模型本身是无状态的：每次请求都是独立的一次计算，服务器不记得上一轮说过什么。所谓"记得上文"，是客户端自己维护 messages 数组，每轮把 system + 全部历史 + 新问题一起发过去，模型看完整个对话才"显得"有记忆。我实测：第一轮说"我叫徐子然"，第二轮问"我刚才说我叫什么"，模型答"你刚才说你叫徐子然"——靠的就是完整 messages。
  • ③ 换个平台你改哪几个值？为什么只改这几个？只改三个值：baseURL、model、apiKey，而且全在 .env 里，代码一行不动。原因是主流大模型平台都兼容 OpenAI 接口格式——请求地址结构（baseURL+/chat/completions）、请求体（model + messages 数组）、响应体（choices[0].message.content）完全一样。所以换平台只是换"门牌号 + 模型名 + 钥匙"，房子的结构不用动。
